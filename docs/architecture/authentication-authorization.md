# Authentication and Authorization

JWT validation checks issuer, audience, lifetime, signing key, an access-token-use claim, user existence, active/deleted state, restriction provenance, a SecurityStamp-derived version, and an active opaque session ID. Password login, refresh rotation, two-factor completion, and step-up proof validation share the provenance guard. Active Administrative/Security Holds and `LegacyUnclassified` rows fail closed even if Identity's `LockoutEnd` is absent or expired; a non-null legacy `LockoutEnd` without provenance also fails closed. Password lockout creation writes an `OrdinaryLockout` row transactionally. Legacy tokens without a version, access-token-use claim, or session ID fail closed; deployment requires the planned Identity migration and the approved classification rollout.

Administrative session revocation at `POST /api/admin/identity/users/{userId}/revoke-sessions` uses the dedicated bearer-authenticated `IdentityAdminSessionRevocationPolicy` for `Superadmin`, the five-per-minute `AuthenticatedSecurityPolicy`, and an actor-bound five-minute `X-Step-Up-Proof`. The proof is validated before target lookup; a valid request atomically rotates the target security version and revokes every target refresh token and session, even for inactive, deleted, or locked targets. It sends no notification and attempts a redacted target-scoped audit after commit without changing the successful response if audit delivery fails. When actor and target are the same, the canonical refresh cookie is cleared.

Administrative unlock at `POST /api/admin/identity/users/{userId}/unlock` uses the dedicated bearer-authenticated `IdentityAdminUserUnlockPolicy`, the same limiter, current authoritative Superadmin membership, and an actor-bound five-minute `X-Step-Up-Proof`. It rejects self-action and releases only an unexpired `OrdinaryLockout` provenance row that agrees with Identity's lockout state. Holds, unclassified rows, legacy mismatches, and ineligible targets fail closed. An actual unlock closes provenance with actor/time, clears the lockout and access-failed count, and atomically invalidates target security state; notification and explicit audit happen after commit and do not change the committed result.

Refresh tokens are stored in `IdentityContext` only as SHA-256 hashes. Each completed login has a random public-ID session; issued access tokens carry that opaque session ID, and bearer validation requires the owned session to remain active and unexpired. Rotations add a child token linked to the presented parent and require a conditional active-session update before storing a replacement token. `GET /api/account/sessions` returns only active sessions owned by the authenticated user and never returns refresh-token material; `DELETE /api/account/sessions/{sessionId}` ends one owner session and its active refresh tokens, requires a step-up proof for another session, and gives the same successful response for unknown or other-account IDs. Reuse of a revoked token invalidates active tokens and sessions for that user only when the token's session is still active; tokens from deliberately ended sessions fail without escalating to account-wide revocation. `POST /api/account/sessions/revoke-all` requires an authenticated user and current step-up proof, revokes every session including the caller's, rotates the security version, and clears the refresh cookie after the Identity transaction commits. Logout revokes the current session and remains non-failing for missing, invalid, expired, or revoked supplied tokens. A daily hosted cleanup removes up to 500 leaf token rows retained for at least seven days after expiry, then up to 500 ended sessions retained for at least 30 days after expiry or revocation. The canonical refresh cookie is `Secure`, `HttpOnly`, `SameSite=Lax`, and scoped to `/api`; transition cleanup also covers legacy paths.

API keys arrive in `X-API-Key`, are compared as SHA-256 hashes, and are eligible only when key and client status permit. Failures intentionally conceal the reason. Raw values are returned only during creation and must never be persisted or logged.

Configured policies are not necessarily applied. Country permission policies exist but are not attached to Country actions; API-client administration lacks explicit authorization; and audit queries require authentication but lack a dedicated role/permission policy. API-client `RateLimitPerMinute` is stored but not enforced. These are risks, not patterns to reproduce.

Documentation and logs may name configuration keys but must never include secret values.
