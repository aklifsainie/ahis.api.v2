# Blueprint: administrative disable of an Identity user

**Status:** Proposed for review. Implementation requires explicit approval of this exact saved revision. The launcher saves this blueprint; this planning task makes no repository changes.

## Outcome and scope

Add `POST /api/admin/identity/users/{userId}/disable` for an eligible human Identity user anywhere in the application. A successful mutation creates an active, provenance-backed `AdministrativeSecurityHold` that blocks authentication until a future enable action releases that hold. This blueprint covers disable only. It adds no tenant boundary, schema, migration, role-management action, or enable endpoint.

## Owning module and confirmed source observations

- `AdminIdentityController` owns the neighboring administrative security-state, revoke-sessions, and unlock routes. Those actions use the custom `IMediator`; Account feature handlers delegate Identity work to `IAccountService` and `AccountService`. `IdentityContext`, `IdentityUnitOfWork`, and `IdentityRestrictionService` own Identity persistence and restriction provenance. This follows the Account feature guidance rather than adding an Application repository.
- `IdentityUserRestriction` already has `OrdinaryLockout`, `AdministrativeSecurityHold`, and `LegacyUnclassified` categories, placement and closure actor fields, timestamps, and origin. `IdentityContext` configures a filtered unique index allowing one active row per user and a check requiring holds to have no expiry. `AddIdentityUserRestrictions` exists in source; documentation says it was generated and reviewed but not applied.
- `IdentityRestrictionService.IsAuthenticationAllowedAsync` denies active holds, unclassified restrictions, and a non-null `LockoutEnd` lacking provenance. Login, refresh, bearer validation, two-factor completion, and step-up validation use the provenance or token-state guard. `IdentityTokenStateService.InvalidateAsync` rotates the SecurityStamp-derived version and revokes active refresh tokens and sessions; the new version invalidates access tokens and actor-bound step-up proofs for the target.
- The neighboring unlock endpoint requires a bearer Superadmin policy, an authoritative current-role check, the authenticated-security limiter, and an actor-bound five-minute `X-Step-Up-Proof`. It validates proof before target lookup and attempts generic notification and actor/target audit after commit. `AuditLogger` writes through a separate `ApplicationDbContext`.
- `Program.cs` configures `AddRoles<IdentityRole>()`, while `IdentityContext` explicitly maps `IdentityRole<string>` to `IdentityRoles`; the initial migration also contains `AspNetRoles`. The separate role-store-alignment blueprint records this unresolved deployment prerequisite. Source alone does not prove the live role table or current assignments.

These are source observations, not new business requirements. The following design rules are owner-confirmed for this endpoint.

## Proposed request flow and owner decisions

1. Add a dedicated bearer-authenticated `IdentityAdminUserDisablePolicy` requiring `IdentityRoleNames.Superadmin`; attach it directly to the action with `AuthenticatedSecurityPolicy`. The controller accepts only route `userId` and the `X-Step-Up-Proof` header, with no request body, and dispatches `DisableAdminUserCommand` with `HttpContext.RequestAborted`. Derive the actor solely from `ICurrentUserService`.
2. Reject a blank actor, blank target, or self-target generically. In the Identity service, verify the actor's current authoritative Superadmin membership and validate the actor-bound five-minute proof before target lookup. Missing, expired, stale, or wrong-actor proof has one generic validation outcome; it cannot reveal target existence. Recheck authorization-sensitive state within the mutation transaction where needed for race safety.
3. In an `IdentityContext` transaction, reread the target and active restriction. A missing target yields the not-found outcome only after authorization and valid proof. An inactive or soft-deleted target is ineligible. An eligible target with an existing active `AdministrativeSecurityHold` returns idempotent `204` without rotating tokens, changing provenance, notification, or audit.
4. For a new hold, reject an active `LegacyUnclassified` row, a non-null legacy `LockoutEnd` without matching ordinary provenance, or inconsistent restriction/Identity state. An ordinary lockout may be converted: require its active provenance and Identity lockout fields to agree at database precision, conditionally close that ordinary row with actor/time, and clear its `LockoutEnd` during conversion so a later hold release cannot leave an unclassified lockout. Preserve `LockoutEnabled`, failed count, credentials, and MFA state. For a clean target, create the hold directly. Retain all closed provenance history; set the new hold's category, start time, server-owned origin, placing actor, and null expiry. Do not infer a category from lockout duration.
5. Prohibit disabling the last **effective** Superadmin. For this guard, count current role members who are active, not soft-deleted, and presently eligible to authenticate under Identity lockout and restriction provenance; the target's effective membership must be considered before placing the hold. Use the authoritative runtime role store. Recheck the count and target eligibility transactionally with a provider-backed serializable or equivalent locking strategy that protects the relevant user, role-membership, and restriction reads. Concurrent disables or changes that could remove the final effective Superadmin must serialize or cause one operation to fail and roll back. Do not rely on a pre-transaction count, a JWT role claim, or an in-memory lock. Fail safely if the authoritative count or locking guarantee cannot be established. Coordinate any other role, deactivation, or restriction writer that can remove effective Superadmin access before exposing this endpoint.
6. Insert the hold and call `IIdentityTokenStateService.InvalidateAsync` in the same transaction. Check every Identity result and affected-row condition; the unique active-row index is the final duplicate guard. Roll back on changed provenance, role/count race, concurrency conflict, failed Identity update, failed token/session invalidation, or commit failure. A committed hold must rotate the target security version/stamp and invalidate access validity, refresh tokens, refresh sessions, and step-up proofs atomically. A race may fail with a generic operational response; it must never disable the last effective Superadmin or leave a partial mutation.
7. Mark commit as confirmed before external effects. After an actual committed mutation, attempt one redacted actor/target audit and one generic target security notification, independently and with cancellation independent of the completed request. Either failure leaves the response at `204`. Do not send either effect for an idempotent active hold. The retained restriction row is the authoritative record even if the separate audit write fails.

## API contract and security

- `POST /api/admin/identity/users/{userId}/disable`; opaque string Identity user ID in the route, `X-Step-Up-Proof` header, no body. No target data or reason is returned. Set `Cache-Control: no-store` and document the contract in Swagger.
- `204 No Content` for a committed hold or an already active hold on an otherwise eligible target. `404 Not Found` only for a missing user after the policy, current-role check, and valid proof. Use one generic `400 Bad Request` for self-targeting, an ineligible target, or missing/invalid proof. Preserve framework `401`, `403`, and `429` behavior. A pre-commit operational failure may yield a sanitized `500`; post-commit audit or notification failure cannot do so.
- Do not return or log the proof, bearer or refresh token, cookie, security stamp/version, hashes, credentials, email address, internal reason/evidence, or unmasked audit values. Audit with `AuditActionEnum.StatusChange`, entity `AccountSecurity`, target ID as entity ID, actor from current-user context, and a fixed label such as `AdminUserDisabled`. Notification text states generically that account access was restricted and gives a support path; it discloses no category or reason.
- Global scope applies to every eligible human Identity user. API-client keys and permission policies cannot satisfy this human bearer policy. No tenant selector or tenant boundary is introduced.

## Future enable boundary

The later enable operation may close **only** an active `AdministrativeSecurityHold`; it must not reactivate inactive or soft-deleted accounts or alter lockout, credential, or MFA state. It requires its own reviewed blueprint and approval. Disable must leave provenance and Identity lockout state coherent so this future boundary is possible; it does not implement or authorize enable.

## Rollout prerequisites, risks, assumptions, and open decisions

- **Separate rollout prerequisite:** `AddIdentityUserRestrictions` must be deployed and the provenance rollout completed, including legacy classification, known writer reconciliation, and authentication enforcement verification, before disable is enabled. This blueprint does not generate or apply a migration or authorize database access or deployment.
- **Separate role prerequisite:** Resolve the `IdentityRole`/`AspNetRoles` versus `IdentityRole<string>`/`IdentityRoles` mismatch under the role-store-alignment blueprint and verify usable current Superadmin membership in the target environment. Do not seed or repair roles here.
- **Inference:** Clearing `LockoutEnd` while converting a proven ordinary lockout is needed because the current authentication guard rejects a non-null lockout end without active ordinary provenance after a later hold release. This affects disable only; it does not authorize future enable to change lockout state. If provider behavior or owner review rejects that conversion detail, stop and revise this blueprint before implementation.
- **Implementation uncertainty:** Prove the SQL Server isolation/locking strategy and all writers that can reduce the effective Superadmin set. If they cannot be coordinated without a schema or broader behavior change, stop and seek a revised approved blueprint. The live migration history, role tables, role assignments, and external writers are environment facts unavailable from repository source.
- **Assumptions:** Identity IDs remain opaque strings; the existing five-minute proof, authenticated-security limiter, token-state invalidation, audit logger, and generic email sender are reused. No owner business-rule decision remains open. Approval applies only to this exact saved blueprint revision; material scope, contract, schema, security, or behavior drift requires a new revision and approval.
