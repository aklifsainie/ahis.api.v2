## Outcome and scope

Retain the r3 design for a one-time, CLI-only `bootstrap-superadmin` command. Its production/bootstrap admission remains exact: `ASPNETCORE_ENVIRONMENT` is `Development`; the fixed `ahis.template.api/appsettings.Development.json` is the configuration trust root; the sole admitted data source is `tcp:172.20.198.156`; the sole admitted database is `AhisApiTemplateV2Db`; and the physical TCP endpoint, port 1433, and current database must be attested at runtime on the bootstrap connection immediately before its serializable transaction. No fixture name, test connection, environment override, or test switch may pass through or relax that admission path.

This revision defines the previously open relational-test fixture decision. The owner permits future consideration of a disposable database on the same Development SQL Server. That permission is design context, not authorization to create, connect to, use, migrate, or delete a database in this planning task. The fixture is only for isolated tests of the Identity service, schema, transactions, and token/session effects. It is never a valid target for the production/bootstrap CLI.

## Observed and proposed flow

Observed partial CLI flow: command dispatch → fixed-file and connection-string checks → SQL connection and attestation → Identity service → serializable transaction. Proposed operational flow remains r3, including a final physical attestation on the transaction connection immediately before mutation.

Proposed test flow: separately approved fixture lifecycle runner → guarded lifecycle connection to `master` for creation → uniquely named fixture database → reviewed Identity migrations and synthetic seed data → test-only `IdentityContext`/Identity manager construction using a fixture connection → relational tests → teardown and explicit deletion verification. The test runner must never call the production/bootstrap CLI with a fixture connection or inject a fixture value into its admission configuration. Static CLI rejection of any fixture target can be tested without opening a database.

## Test-only fixture boundary and connection design

- Use a dedicated test-only fixture component under `ahis.template.test/TestFeatures/IdentityFeature/` or a narrowly scoped test support folder. It is constructed only by opted-in relational tests. Normal application and CLI dependency injection must not register or discover it. Do not add an application configuration switch, environment override, alternate bootstrap target, or public CLI argument.
- Assign one immutable run identifier before any connection. The exact database name is `AhisApiTemplate_BootstrapTest_` followed by 32 lowercase hexadecimal characters derived from a newly generated run GUID. Persist that name only in the test process for create, use, and drop. This format is deterministic within the run, unique across runs to practical certainty, and within SQL Server identifier limits. Reject any name that fails the exact prefix and suffix grammar, is reused from another run, or equals `AhisApiTemplateV2Db` under both ordinal-ignore-case and SQL Server database-name collation comparison. Validate the guard before constructing **every** lifecycle or test connection and before every create, migrate, seed, test, cleanup, or drop operation.
- Before creation, use a separately supplied test lifecycle connection whose initial catalog is `master` and whose endpoint is confirmed as the owner-designated Development SQL Server. Perform a read-only collision query for the exact generated name. Refuse if it exists; never attach to, migrate, clear, or drop an existing database. Recheck immediately before `CREATE DATABASE` and handle a concurrent creation as refusal. Quote the validated identifier safely in SQL; never build SQL from an unchecked name.
- Construct the fixture data connection explicitly in test code from a dedicated test credential source using `SqlConnectionStringBuilder`, setting `InitialCatalog` to the validated fixture name. Do not copy or modify the fixed operational JSON, use its credential, use merged application configuration, or call `FirstSuperadminBootstrapCli.RunAsync` for fixture work. Inject the fixture connection or `DbContextOptions<IdentityContext>` into a test-only service provider that registers only the Identity collaborators needed by each test. The production CLI continues to reject every database except `AhisApiTemplateV2Db` before it opens a connection.
- Confirm non-production status before the creation gate: the operator identifies the Development SQL Server as non-production, confirms its physical endpoint and intended fixture permissions, and confirms that the fixture name is distinct from the operational database. A `Development` label alone is insufficient. If endpoint identity, database classification, permission scope, or the name guard cannot be established, do not create the fixture.
- Use separate lifecycle and test principals where supported. Grant the lifecycle principal only the server/database privileges needed to create and drop this fixture; grant the test principal only the privileges needed to migrate and test inside that fixture. Neither principal should have rights to alter or drop `AhisApiTemplateV2Db`. If the available SQL permission model cannot enforce this scope, stop for a separately reviewed access design. Never print connection strings, credentials, user identifiers, raw tokens, security stamps, or sensitive exception details in test output, command output, or retained artifacts.

## Fixture lifecycle and failure handling

1. Obtain all three explicit fixture approvals below, including advance approval for failure cleanup, before any fixture creation. Acquire test credentials through the approved secret mechanism without writing them to repository files or logs. Confirm non-production endpoint, name grammar, operational-name exclusion, and privileges.
2. Create only the absent generated database. Record a nonsensitive run ID and fixture name in the test process. Do not modify the operational database or any pre-existing database.
3. Apply the already generated, source-reviewed Identity migrations to the fixture only, in dependency order, including the role-store alignment prerequisite and marker migration. Check migration history and schema in the fixture. Do not regenerate or apply migrations elsewhere. Seed only synthetic users, restrictions, roles, sessions, and hashed refresh-token data required by each case; isolate or reset test state between cases without deleting the fixture marker to simulate a new bootstrap attempt.
4. Execute relational tests only through the test-only provider. Keep test execution serial unless each parallel worker has its own separately named fixture and approvals. Close and dispose contexts, readers, transactions, and connections before teardown.
5. In a `finally` path after success, assertion failure, exception, cancellation, or timeout, attempt approved cleanup and drop of the exact recorded fixture. Check the name guard again before deletion. Terminate only sessions belonging to that fixture if necessary and expressly authorized; never terminate sessions on the operational database. Do not use a broad prefix-based deletion query. If drop fails, report the fixture name and nonsensitive failure category to the operator for controlled cleanup; never silently mark cleanup complete or fall back to another database.
6. After drop, query `sys.databases` from `master` for the exact name and require absence. Record this post-test deletion verification as a pass/fail result without secrets. A missing or inconclusive verification is a failed cleanup requiring operator follow-up. Also verify the operational database was never selected for test DDL or cleanup through connection and command guards; do not query or change its data as part of the fixture test.

## Test plan

**Pure admission tests, no database:** Cover exact command, environment, fixed-file trust root, duplicate/ambiguous connection-string keys, override attempts, malformed targets, fixture-name rejection, and generic output. Assert refusal occurs before any connection or HTTP host startup. Use synthetic values without credentials.

**Fixture relational tests, only after all fixture gates:** Verify migration order and schema; canonical role seed without user assignments; successful single bootstrap and redacted marker; second invocation refusal; missing, inactive, deleted, unconfirmed, locked, restricted, legacy-unclassified, or already assigned targets; absence of a prior Superadmin assignment; and exactly one resulting role. Run competing attempts against one fixture to prove one winner and one marker. Inject failure and cancellation before commit to prove rollback of role, marker, security stamp, refresh-token revocation, and session revocation. Exercise uncertain commit handling without a second assignment. Verify old JWT/security version and existing sessions are rejected and a fresh login can receive the role claim. Test guarded migration `Down` on a populated fixture only when that test can leave the fixture safely disposable. Record only nonsensitive assertions.

**Runtime attestation tests:** Use a controlled seam or connection double for null metadata, wrong transport, wrong address, wrong port, wrong current database, reconnection, and timing/connection identity. Any live SQL test uses only the fixture connection and never relaxes operational CLI admission. The fixture can prove service and SQL transaction behavior; it cannot stand in for a successful operational CLI invocation because its database name must be rejected.

**Deletion check:** Treat verified absence of the exact fixture name in `sys.databases` as a required test-run result. A failed test run with successful deletion is reported as test failure plus cleanup success; a successful assertion run with failed or unverified deletion is not complete.

## Risks, assumptions, and open decisions

**Risks:** A test harness that reuses operational configuration or exposes a database-name override to the CLI could bypass the intended boundary. SQL aliases, redirects, or privileges may obscure the actual fixture target. A failed cleanup can leave a database behind. Parallel tests can collide or interfere if they share a fixture. Logs can expose credentials or token material. The current partial implementation may differ from r3 and needs focused review before acceptance.

**Assumptions:** The owner-designated SQL Server is confirmed non-production before fixture approval; its connectivity and privileges are not verified here. Existing migrations can be applied to a clean fixture in the reviewed order. A separate test credential mechanism can be provided without changing repository configuration. The GUID-derived name is unique for each run, and a collision causes refusal rather than reuse.

**Open decisions for later gates:** Select the lifecycle and test principals and secret delivery mechanism; confirm the server's non-production classification and exact physical endpoint; review any test project reference or package need; decide the operator and procedure for failed-drop escalation; and review the existing partial CLI, service, and migrations against r3 before implementation resumes. None of these decisions may relax the exact operational CLI target rule.
