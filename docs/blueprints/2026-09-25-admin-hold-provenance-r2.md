# Blueprint: authoritative administrative hold provenance (revision 2)

**Status:** Proposed for approval. This is a new revision for review. Implementation, migration generation, database access, deployment, and the separate administrative unlock change require their own authorization. The eleven owner decisions below are resolved design requirements.

## Outcome and scope

Make restriction provenance in `IdentityContext` authoritative for ordinary Identity lockouts, non-expiring Administrative/Security Holds, and ambiguous legacy lockouts. A hold must remain effective without a sentinel `LockoutEnd`. Every authentication and credential-validation path must fail closed for an active hold or `LegacyUnclassified` restriction. This increment provides the schema, internal writers, classification mechanism, enforcement, and phased rollout design. It adds **no hold placement or release public API**; either endpoint requires a separate approved blueprint.

## Owning module and source evidence

Identity owns `ApplicationUser`, `IdentityContext`, `IdentityUnitOfWork`, `AuthenticationService`, `AccountService`, `IdentityTokenStateService`, and `AccountSecurityProofService`. `AuthenticationService.LoginAsync` uses `PasswordSignInAsync(..., lockoutOnFailure: true)`; repository search found no other application lockout writer. `ApplicationUser.IsLockedOut` and `IdentityTokenStateService.IsEligible` currently depend on a future `LockoutEnd`. Refresh uses `Matches`; bearer validation in `Program.cs` uses `ValidateAsync`; step-up proof validation calls token-state validation. Two-factor completion also checks token state. These checks currently cannot distinguish an ordinary lockout from an administrative hold. `IdentityContext` owns users, refresh tokens, and sessions, and `IdentityUnitOfWork` provides the transaction boundary. `IIdentityTokenStateService.InvalidateAsync` rotates the security stamp and revokes refresh tokens and sessions. Explicit `IAuditLogger` writes through the separate `ApplicationDbContext` and is best effort.

The prior `docs/blueprints/2026-09-25-admin-user-unlock.md` explicitly identifies missing hold provenance and proposes a conservative time-window classifier. That classifier is insufficient once provenance is authoritative. The role-store mismatch and its investigation are documented in `docs/blueprints/2026-09-25-identity-role-store-alignment.md`. No existing provenance plan or implementation was found under `docs/blueprints/` or the searched Identity source.

## Resolved business behavior and proposed flow

1. Categories are `OrdinaryLockout`, `AdministrativeSecurityHold`, and `LegacyUnclassified`. Administrative/Security Hold is **one non-expiring category**. `LegacyUnclassified` remains blocking regardless of the current or expired `LockoutEnd` until classified. Ordinary lockouts expire according to their recorded expiry. At most one restriction row with `EndedAtUtc IS NULL` may exist per user.
2. Placement, release, and legacy classification are Superadmin-only, globally scoped, require a current actor-bound step-up proof, and reject **every self-action**, including an otherwise harmless or idempotent request. Resolve the actor from authenticated server context; never trust a caller-supplied actor ID or an API-client principal. Internal service methods must verify a fresh authoritative Superadmin role membership and the proof before target lookup or mutation. No public route is added here.
3. Placement locks the target through an active provenance row rather than a far-future `LockoutEnd`; it atomically invalidates the target security stamp, access-token validity, refresh tokens, sessions, and step-up proofs. Release closes only a proven active Administrative/Security Hold and **invalidates that state again** in the same transaction. Do not treat an ordinary or unclassified restriction as releasable. A failed operation leaves the previous restriction and token state intact. Concurrency is rechecked inside the transaction; duplicate or racing placements fail safely.
4. After a confirmed placement or release commit, attempt one generic target notification. It states only that account access was restricted or restored and how to contact support; it contains no reason, category detail, credentials, token, or proof. Delivery failure cannot change the committed outcome. An explicit actor/target audit is also attempted after commit and is best effort; the transactional restriction row is authoritative.
5. Login, refresh rotation, bearer validation, two-factor completion, and step-up proof validation must consult the same effective-restriction rule. No token or proof may be issued after a blocking restriction becomes visible. Recheck immediately before issuance/commit where a flow spans multiple reads. An unavailable or inconsistent provenance read fails closed. Existing inactive/deleted checks remain. The administrative security-state projection should derive its `IsLockedOut` value from the effective restriction, without adding a new public response field in this increment.
6. The existing Identity password-failure writer must create or update an `OrdinaryLockout` row transactionally with the Identity lockout transition. It must close an expired ordinary row before creating another active row. It must never overwrite or clear a hold or `LegacyUnclassified` row. If the ordinary writer cannot persist provenance, roll back the lockout transition and fail safely. Prevent other known writers from bypassing this boundary before enforcement is enabled.
7. Closed provenance, classification decisions, actors, and timestamps are retained indefinitely pending a separately approved retention policy. Neither cleanup jobs nor release delete them.

## Entity, migration, and retention design

Create an `IdentityUserRestrictions` table with an opaque primary key; required `UserId` foreign key to `IdentityUsers` with restricted deletion; category; `StartedAtUtc`; nullable `ExpiresAtUtc` (required only for ordinary lockout); nullable `EndedAtUtc`; origin/source; nullable `PlacedByUserId` for automated ordinary lockouts; and nullable `EndedByUserId`. Store a bounded, access-controlled internal reason code or sanitized note if needed by operations; never put its text into notifications, public responses, or cross-context audit payloads. Preserve actor IDs and event times when a row closes. Add a unique SQL Server filtered index on `UserId WHERE EndedAtUtc IS NULL`, indexes for target/history and category review, and check constraints for category/expiry and end-time consistency. Normal application code may close a row but may not delete or repurpose its original category.

Represent each ambiguous legacy case by an active `LegacyUnclassified` row. On review, close it with `ReviewedByUserId`, `ReviewedAtUtc`, a decision (`OrdinaryLockout`, `AdministrativeSecurityHold`, or `NotRestricted`), and a non-sensitive evidence reference. In the same transaction, create an ordinary or hold row when the decision requires an active restriction and align any legacy `LockoutEnd` state. A decision that an ordinary lockout already expired closes the legacy row without an active successor. Keep the original row and decision indefinitely. Invalidate target token/session/proof state at classification, including when a case is cleared, so preclassification credentials cannot revive. The unique index enforces one active row throughout each transition.

Generate the migration only after this blueprint and the migration step receive approval, using `IdentityContext` and the repository migration workflow. Inspect `Up`, `Down`, designer, and snapshot. Migration `Down` must refuse to drop populated provenance or classification data; an empty, unused table may be removable. Never use a rollback that discards populated records.

## Legacy inventory, rollout, and rollback

**Phase 1 — schema and writers:** Inspect each target environment's `__EFMigrationsHistory` and actual Identity schema before applying a migration. Review the full history of applied Identity migrations, inventory every non-default lockout state (including non-null `LockoutEnd`, nonzero `AccessFailedCount`, and `LockoutEnabled` values differing from the configured/default expectation), and document known external jobs, applications, scripts, or operators that write these fields. Deploy the schema and provenance-capable writers with enforcement disabled only for the controlled transition. Do not permit new administrative holds or classification-dependent unlocks during this gap. Any known external lockout writer must be routed through the transactional writer or disabled before Phase 3. Environment database reads and migration application require separate authorization.

**Phase 2 — inventory and classification:** Reconcile the inventory with migration history and writer evidence. Create `LegacyUnclassified` records for every ambiguous lockout before treating it as ordinary; do not infer its type solely from duration or an expired end value. A different authenticated Superadmin reviews the documented inventory and records a per-user decision and evidence reference for every ambiguous case through a controlled, auditable internal classification path. Self-classification is prohibited. Reconcile counts, duplicate candidates, changed users, and late writers; rerun the inventory until no unreviewed ambiguous case remains. Prove that every classified row has its actor, time, decision, and evidence reference.

**Phase 3 — enforcement:** Enable the shared provenance guard only after schema/writer deployment, completed classification, writer reconciliation, and focused verification. Verify login, refresh, bearer, two-factor, proof, and administrative security-state behavior in the target environment. Monitor failed provenance reads and state mismatches; deny access on those failures. The switch and its production change require separate deployment authorization.

Production rollback is forward remediation: correct code, data, or configuration while preserving all populated provenance. Do not revert to an older binary that can admit a held or unclassified user. If remediation cannot keep enforcement intact, restrict authentication or keep the affected environment in maintenance until a safe forward fix is deployed. Never drop populated provenance records.

## Authorization, audit, and transaction impact

Administrative operations use a bearer human principal, fresh Superadmin role check, actor-bound step-up proof, target lookup only after proof, and a target ID distinct from actor ID. Apply the same global scope and self-action prohibition to placement, release, and classification. Their internal result must not expose a sensitive reason. A later endpoint blueprint must separately define route, policy, rate limit, request and response contract, and disclosure rules.

Within one `IdentityContext` transaction, write or close provenance, align Identity lockout fields when required, and call `IIdentityTokenStateService.InvalidateAsync`; commit only after every step succeeds. Use concurrency-aware updates and the unique index as the final duplicate guard. Track whether commit was confirmed so cancellation or post-commit side-effect failure cannot report a committed operation as failed. After commit, attempt `IAuditLogger` with fixed action labels and actor/target IDs, and send the generic notification with cancellation independent of the completed transaction. The separate `ApplicationDbContext` audit remains best effort and cannot substitute for provenance.

## Test plan and validation after approval

Unit tests: category and expiry rules; hold and unclassified fail closed even with null or expired `LockoutEnd`; ordinary expiry; actor role, proof, global scope, and every self-action rejection; generic notifications; no reason leakage; post-commit audit or email failure preserves success; release invalidates state again; classification records a per-user decision.

Relational tests: filtered unique index; two concurrent placements; ordinary lockout/provenance atomicity; classification close-and-create atomicity; rollback on failed token invalidation; closed record retention; migration `Up` and guarded `Down`; production-like legacy states. Authenticated API and service tests: login, refresh, bearer, two-factor, and step-up denial for hold and `LegacyUnclassified`; stale access/refresh/proof rejection after placement, classification, and release; no hold-management route; existing security-state response remains redacted. Test a missing or unavailable provenance read and a late external-style lockout mismatch as fail-closed conditions.

Run focused tests first, then concise solution checks after implementation approval: `dotnet test .\ahis.template.test\ahis.template.test.csproj --filter "FullyQualifiedName~Restriction|FullyQualifiedName~Lockout" --verbosity quiet`; `dotnet restore .\AhisApiTemplate.sln --verbosity quiet`; `dotnet build .\AhisApiTemplate.sln --no-restore --verbosity quiet`; `dotnet test .\AhisApiTemplate.sln --no-build --no-restore --verbosity quiet`. Inspect focused failures rather than broad output. Do not use `dotnet ef database update` as verification.

## Risks, assumptions, and remaining technical dependencies

The role-store mismatch documented in `2026-09-25-identity-role-store-alignment.md` must be resolved and a usable Superadmin role membership verified before administrative classification or later hold operations can run. Actual migration history, live lockout states, and external writers are environment-specific and cannot be established from repository source; their documented inventory is a rollout prerequisite, not an unresolved policy question. Transaction boundaries around Identity's automatic failed-sign-in update and the exact controlled classification tool must be verified against the provider and deployed topology during implementation. Any writer that cannot participate in the authoritative transaction blocks enforcement rollout until repaired or disabled. Assume Identity user IDs remain opaque strings and the existing security-version, email sender, and audit facilities are reused. All eleven owner policy decisions stated in the request are resolved by this design.
