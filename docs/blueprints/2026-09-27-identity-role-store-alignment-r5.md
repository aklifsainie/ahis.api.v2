# Identity role-store alignment and initial role seeding — revision 5

**Status:** Proposed for review. This revision supersedes r4 for the stated Local Development findings. Preserve r4 and earlier blueprints as historical context. Approval applies only to this revision and does not authorize implementation, migration generation, migration application, or deployment.

## Outcome and scope

Align the Identity runtime role store and EF model on `AspNetRoles` for **Local Development**, then seed exactly two protected system roles: `Superadmin` and `User` (`NormalizedName` values `SUPERADMIN` and `USER`). Protected means future role-management work must prevent deletion and unsafe renaming; this prerequisite does not add that API. Do not assign either role to a user, create a bootstrap path, add role claims, or implement role-management or other P2 actions. Existing roles and relationships in any target must be preserved.

`AspNetRoles` is selected only for the stated Local Development evidence. Each other environment needs separate read-only discovery, migration-application approval, and deployment approval. An unexpected schema, row, dependency, or conflict requires a revised blueprint before implementation for that environment.

## Owning module and analogous implementation

`ahis.template.identity` owns `IdentityContext`, the Identity role model and migrations. `ahis.template.api` registers Identity and authorization policies. `AuthenticationService` issues JWT role claims; `AccountService` checks current membership for unlock. Multi-step Identity work belongs in Identity services. Country repository/unit-of-work, API-client direct-service, and audit Application-side EF patterns do not govern this change. No custom mediator request or public endpoint is added.

## Evidence and confidence

**Confirmed repository source:** `ahis.template.api/Program.cs` registers `AddIdentityCore<ApplicationUser>().AddRoles<IdentityRole>().AddEntityFrameworkStores<IdentityContext>()`. `ahis.template.identity/Contexts/IdentityContext.cs` separately maps `IdentityRole<string>` to `IdentityRoles`. `ahis.template.identity/Migrations/IdentityContextModelSnapshot.cs` contains concrete `IdentityRole` on `AspNetRoles`, with unique filtered `RoleNameIndex`, and base `IdentityRole<string>` on `IdentityRoles`. `ahis.template.identity/Migrations/20260824144538_IdentityInitialMigration.cs` creates both tables; `IdentityUserRoles.RoleId` and `IdentityRoleClaims.RoleId` reference `AspNetRoles.Id` with cascade delete. `ahis.template.identity/Security/IdentityRoleNames.cs` already defines `Superadmin` and `User`. `AuthenticationService` obtains roles through `UserManager.GetRolesAsync` and adds `ClaimTypes.Role`; `Program.cs` policies require `Superadmin`; `AdminIdentityController` applies those policies to security-state, revoke-sessions, and unlock actions. `AccountService` also checks current Superadmin membership for unlock.

**Owner-authorized Local Development read-only findings, not independently queried in this planning task:** migration history contains `20260824144538_IdentityInitialMigration`, `20260921061659_AddRefreshTokenSecurityVersion`, `20260921074330_ReplaceRefreshTokensWithHashedSessionModel`, `20260921082113_RemoveApplicationUserRecoveryCodes`, `20260922081341_AddAccountRecovery`, and `20260925062837_AddIdentityUserRestrictions`. `AspNetRoles`, `IdentityRoles`, `IdentityUserRoles`, and `IdentityRoleClaims` exist. Both relationship foreign keys target `AspNetRoles.Id` with cascade delete. `AspNetRoles` has unique `RoleNameIndex` on `NormalizedName`; `IdentityRoles` has only its primary key. All four tables have zero rows. Neither role table has `SUPERADMIN` or `USER` or duplicate normalized names. These findings support `AspNetRoles` as the Local Development runtime relationship target and `IdentityRoles` as empty and unreferenced there. They do not establish another environment's state.

**Inference:** removing the extra base-role mapping should leave one concrete role entity mapped to `AspNetRoles`; EF's generated migration should remove the redundant table without changing the runtime relationship targets. Confirm that in the generated model, operations, and SQL before approval to apply.

## Observed and proposed flow

Current: Identity registration → EF role store → `AspNetRoles`; user-role and role-claim relationships → `AspNetRoles`; login → `UserManager.GetRolesAsync` → `ClaimTypes.Role` in JWT → bearer validation → applicable `RequireRole(Superadmin)` policy. Proposed: retain this path, remove the duplicate `IdentityRole<string>` mapping, and seed the two named roles into `AspNetRoles`. No request/response contract, user assignment, role claim, or authentication configuration changes.

## Business behavior, authorization, and security

The seed creates roles, not access. In the empty Local Development state, no user becomes Superadmin, so Superadmin routes remain unavailable until a separately designed and approved assignment/bootstrap process exists. Future role management must protect these two names; this blueprint does not claim such enforcement already exists. Human Identity roles remain separate from API-client permissions.

Validate the actual controller attributes and policy registration, including the security-read policy's use of the configured default bearer scheme and the explicit bearer schemes on revoke-sessions and unlock. Test a freshly issued JWT for an already assigned **test fixture** Superadmin, a User-only or unassigned test principal, and an invalid or stale token. Confirm `ClaimTypes.Role` is recognized by authorization and the unlock service's current-membership check. JWT role claims are snapshots; token invalidation after later role changes remains a separate P2 decision. Never place token or credential values in documentation or test output.

## Persistence, migration, and rollback

The migration targets `IdentityContext` in `ahis.template.identity`, with `ahis.template.api` as startup project. Local Development's six reported history entries and four empty tables make an empty-table drop and two-role insert a candidate there. Before generating or applying, independently recheck the named target's migration history, schemas, indexes, foreign keys, table counts, normalized-name conflicts, and other database-object or application dependencies. Record aggregate, non-sensitive evidence only. Other environments must satisfy the same checks separately; do not copy the Local Development conclusion to them.

Review a guarded SQL Server operation sequence: verify preconditions; verify `IdentityRoles` is empty and unreferenced; verify `AspNetRoles` and its uniqueness/index semantics; reject conflicting names or IDs; drop only `IdentityRoles`; insert only missing `Superadmin` and `User` rows; verify exactly one normalized row per protected name, expected role counts, unchanged pre-existing IDs, unchanged assignment/claim counts and foreign keys. Keep checks and mutations in a transaction where supported. Do not allow a generated table rebuild, `AspNetRoles` drop, cascade loss, broad update, or implicit `HasData` rewrite. Inspect `Up`, `Down`, designer, snapshot, and generated SQL; edit the generated migration only within the approved design.

Rollback is a separate reviewed operation. A safe `Down` must recreate the old empty `IdentityRoles` schema only after guarding any reversal of the two migration-owned rows. It may remove only rows with the migration's fixed IDs that remain unchanged and have no user-role or role-claim dependents; otherwise it must throw and preserve data. Pre-existing matching roles must never be removed. For a deployed environment with later role use, prefer a reviewed compensating migration or verified restore rather than forcing `Down`. Approve backup/restore readiness, recovery point, operator, and post-rollback checks before application. Preserve role IDs, all assignments and claims, and unrelated Identity data.

## Risks, assumptions, and open decisions

**Risks:** seeding `IdentityRoles` would miss the runtime store; dropping an unexpectedly populated or depended-on table could lose data; name or collation conflicts could duplicate roles; a generated migration could rebuild relationship tables; JWTs can retain old role claims; Superadmin endpoints remain inaccessible without an assignment.

**Assumptions:** the owner-authorized Local Development findings are current at review time; the initial catalog is exactly protected `Superadmin` and `User`; no user assignment or bootstrap is authorized. Repository source confirms intended model and migration operations but does not prove another environment's state.

**Open decisions before later gates:** fixed seed IDs and exact guarded SQL; test host and SQL Server fixture strategy; each other environment's role/dependency state; environment-specific backup and rollback method; eventual first-administrator and role-change token policy. Resolve material new findings in a revised, reviewed blueprint.
