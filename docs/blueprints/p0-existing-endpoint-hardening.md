# P0 existing endpoint hardening — proposed blueprint

Status: approved and implemented 2026-09-21. Scope: the seven items that were unchecked under **P0 — Existing endpoint hardening** in [the backlog](../backlog/identity-security-endpoints.md). The authenticator-key replacement item was already complete and remained a regression concern rather than a new feature.

## Outcome and ownership

Close the public password-setup gap; remove production token diagnostics; require a short-lived pre-authentication challenge for 2FA completion; conceal account existence in recovery responses; make refresh-cookie handling consistent; assign a rate-limit policy to every authentication and recovery action; and remove the extra plaintext recovery-code copy.

HTTP contracts and cookie/rate-limit configuration belong to `ahis.template.api`. Requests and handlers use the custom mediator in `ahis.template.application`. Identity token, password, 2FA, recovery-code, and email operations stay in `ahis.template.identity` behind `IAccountService` and `IAuthenticationService`. The closest examples are `ConfirmEmailCommand`/`AccountService.ConfirmEmailAsync`, `VerifyTwoFactorLoginCommand`/`AuthenticationService.VerifyTwoFactorAsync`, and the existing account-security handlers. Do not add an Application repository around Identity managers.

## Observed flow and proposed flow

| Item | Observed source behavior | Proposed behavior |
| --- | --- | --- |
| Initial password | `POST /api/account/set-password` has no authorization, accepts `UserId` plus password, and `SetPasswordFirstTimeAsync` checks only user existence and absence of a password. | After successful email confirmation, send a purpose-specific setup link to the confirmed address. `set-password` accepts user ID only as a lookup key, plus setup token and new password. Verify token, confirmed/active/not-deleted state, and no existing password before `AddPasswordAsync`. Return a generic invalid/expired/used-token error; never authorize using user ID alone. |
| Diagnostics | Public `decode-token` returns claims/payload; public `encode-token` signs caller-shaped claims. | Remove both HTTP actions and their unused mediator queries; remove the unused diagnostic service methods. Do not publish a replacement policy in this increment. |
| 2FA completion | Password login returns `RequiresTwoFactor` without an access token. The `verify-2fa` handler instead requires `ICurrentUserService.UserId`, ignores the submitted `UserId` for verification, and the Identity service calls `SignInManager`'s 2FA methods. | Reuse Identity's protected `TwoFactorUserIdScheme` cookie created by password sign-in as the opaque challenge. Configure a five-minute non-sliding lifetime, `Secure`, `HttpOnly`, and suitable `SameSite`; bind it to the security version at password validation. At completion obtain the user from `GetTwoFactorAuthenticationUserAsync`, verify challenge version and active/unlocked state, then use `SignInManager` for authenticator or recovery-code verification. Remove `UserId` and `ICurrentUserService` from the completion request. Clear the challenge on success and terminal failure. Never issue a JWT or refresh token before completion. [The .NET 8 SignInManager source](https://github.com/dotnet/aspnetcore/blob/v8.0.8/src/Identity/Core/src/SignInManager.cs) confirms the temporary scheme and 2FA methods. |
| Enumeration | Unknown email produces a 400 in forgot-password and resend-confirmation. `check-account` returns different flags for existing and unknown users. Resend currently requires a bearer token, even though unconfirmed users cannot normally sign in. | Return the same 204 for syntactically valid forgot/resend requests regardless of account existence, confirmation state, active state, or mail delivery; retain a 400 for malformed input. Make resend anonymous. Remove the anonymous `check-account` action because its status flags reveal account state; clients should use the confirmation/setup emails and login flow. Keep credential failures generic. |
| Refresh cookie | Login/refresh issue `refresh_token` at `/` with `Lax`; 2FA issues it at `/api/authentication/refresh` with `Strict`, which does not match the `refresh-token` route. Logout clears only the latter path. Account security actions clear both paths. | Centralize append/delete in one API helper. Use host-only `refresh_token`, `Path=/api`, `Secure=true`, `HttpOnly=true`, `SameSite=Lax`, and the actual refresh expiry for all issuance paths. Clear the exact canonical cookie on logout and invalidation, and clear both legacy paths during transition. Never put refresh tokens in response bodies or logs. |
| Rate limits | `AuthPolicy` is a single fixed-window limiter shared across all callers, attached to selected actions; other sensitive actions have no annotation. | Replace the shared bucket with partitioned policies. Apply an explicit decision to every action in the inventory below. Prefer per-client-IP limits for anonymous endpoints and per-user limits for authenticated security actions; keep Identity lockout for credential attempts. Do not trust forwarded IP headers unless the reverse proxy is configured as trusted. Return a generic 429. |
| Recovery codes | `EnableAuthenticatorAsync` generates codes through Identity, then serializes the same plaintext codes into `ApplicationUser.RecoveryCodes`; reset/disable clear the extra column. | Keep Identity's token store as the only persisted source. Return generated codes once from successful enable. Remove the property and all assignments, check each Identity operation result, and prevent repeated enable from regenerating codes. Roll back the Identity transaction if enabling or code generation fails. |

The setup token should use a separately named ASP.NET Core Identity data-protection token provider with a proposed 30-minute lifetime and a distinct `InitialPasswordSetup` purpose. Generate it only after email confirmation has committed. The existing security stamp binds the token to the user; a successful `AddPasswordAsync` rotates that stamp, so later validation fails. Verify this behavior, including concurrent submissions, with the actual Identity store. If a strict single outstanding token is required before successful password creation, add a hashed nonce and a separate schema proposal rather than treating a stateless token as single issuance. A confirmed account with no password can request another setup email through the generic resend endpoint; a delivery failure after confirmation must leave that recovery path available. The setup email must use a server-configured or allow-listed callback origin, since the current client-supplied callback base URL crosses a trust boundary.

For 2FA, keep the Identity temporary cookie so `SignInManager` continues to own lockout and recovery-code redemption. After password validation returns `RequiresTwoFactor`, an Identity-owned challenge helper should reissue that protected ticket with the user's current security-version claim and an explicit five-minute expiry. On completion, authenticate that same scheme, resolve its user through `GetTwoFactorAuthenticationUserAsync`, and compare the ticket's version with current Identity state before calling the 2FA sign-in method. The challenge cookie should be host-only and scoped to `/api/authentication`. Reject missing, expired, mismatched, inactive, deleted, or locked-out challenges uniformly.

## Public API and authorization decisions

| Action | Contract and authorization | Rate-limit decision |
| --- | --- | --- |
| `register`, `confirm-email`, `set-password`, `resend-confirmation-email` | Anonymous. Setup requires its purpose-bound token; resend is always generic 204. | Per IP, strict for issuing mail or consuming setup tokens. |
| `login`, `verify-2fa`, `forgot-password`, `reset-password` | Anonymous. 2FA requires the protected challenge; reset/setup require their respective tokens. Generic credential/token failure. | Per IP, strict; retain Identity lockout for password and authenticator attempts. Recovery-code attempts also need throttling because Identity does not increment lockout for them. |
| `refresh-token`, `logout` | Anonymous with refresh cookie; logout remains idempotent. | Per IP, a separate rotation/logout budget. |
| `check-account`, `encode-token`, `decode-token` | Remove routes and Swagger exposure. | No remaining endpoint. |
| `generate-authenticator-setup`, `enable-2fa`, `disable-2fa`, `change-password`, `re-authenticate`, `2fa/reset-authenticator`, `change-email/request`, `change-email/confirm`, `deactivate` | Retain current bearer/step-up requirements, except the existing anonymous email-confirm action. Review each sensitive action's failure shape. | Explicit per-user or per-IP policy as appropriate; preserve the existing policy where it already applies until replacement is verified. |

Suggested initial policy is five attempts per minute per IP for credential and mail actions, a separate bounded budget for refresh/logout, and five attempts per minute per authenticated user for security changes. These numbers are a proposal, not an observed product requirement. Because ASP.NET Core's in-memory limiter is per API instance, multi-instance deployments need a shared edge/distributed limit before this is treated as an account-wide abuse control. Avoid using a raw email address as a limiter key or log field. Count 429s and security outcomes without recording passwords, tokens, codes, authenticator keys, or full recovery links.

Cookie settings assume same-site browser clients. A cross-site frontend would require `SameSite=None`, credentialed CORS, and explicit CSRF protection for cookie-backed actions; confirm deployment topology before selecting that alternative. Preserve one canonical path through login, 2FA, refresh, logout, and account-security invalidation. Check whether Identity's application sign-in cookie is being emitted alongside JWTs and remove it if unused by this API.

## Files and persistence impact

- Modify `ahis.template.api/Controllers/v1/AccountController.cs`, `AuthenticationController.cs`, and `Program.cs`; add a small API cookie-options/helper type if it prevents divergent settings. Update Swagger comments and response types.
- Modify the affected Account and Authentication mediator requests/handlers, `IAccountService`, `IAuthenticationService`, `AccountService`, and `AuthenticationService`. Remove `EncodeTokenQuery.cs` and `DecodeTokenQuery.cs` after confirming no caller remains. Keep `IIdentityTokenStateService` as the security-version check.
- Modify `ApplicationUser` to remove `RecoveryCodes`; generate and **review** one `IdentityContext` migration that drops only that column and updates the snapshot. Do not apply the migration as verification. No `ApplicationDbContext` change is planned. The password-setup token and temporary 2FA cookie need no new table under the proposed design.
- Leave Country, API-client, audit-query, P1/P2 endpoint, and refresh-session schema work outside this blueprint. The already generated session-model migration is a deployment prerequisite; verify its real deployment state before rollout rather than relying on backlog status text.

Removing the extra recovery-code column deletes existing plaintext copies. Confirm the Identity token store contains the active codes before rollout; test an already enrolled user's recovery-code login after the migration. A rollback of this migration restores the column structure but cannot restore deleted plaintext values; do not repopulate it. Older clients sending a user ID for 2FA or using `check-account`/diagnostics will need a coordinated contract update. Clear legacy refresh cookies on rollout and require re-login if old cookie behavior cannot be made compatible.

## Transactions, audit, and integration

Use `IdentityUnitOfWork` only around Identity changes that must commit together, especially MFA enable and any setup-token consumption coupled to password creation. Confirm email before issuing the setup token; mail delivery is external and cannot be included in the database transaction. Generic public responses must not hide delivery failures from internal operational telemetry. Add targeted security audit events for setup completion, 2FA completion/failure, and recovery requests using the existing `IAuditLogger` pattern; store event type, time, and safe user/correlation identifiers only. Its explicit writes are best-effort, so do not treat them as part of the Identity transaction.

## Implementation sequence and tests

1. Remove diagnostics and add route-level tests proving both paths are absent.
2. Centralize refresh-cookie options and test every issue/clear path, including removal of both legacy paths.
3. Add the temporary 2FA challenge binding, change the request contract, and test missing/expired/wrong-version challenge, wrong-user input, lockout, authenticator success, recovery-code use, and no token before success.
4. Add initial-password token issuance/delivery and validation; test wrong purpose/user, expiry, replay after success, concurrent use, already-set password, inactive/deleted/unconfirmed user, and delivery retry.
5. Normalize forgot/resend responses and remove `check-account`; test existing, absent, confirmed, unconfirmed, inactive, and SMTP-failure cases produce indistinguishable public results for valid input.
6. Remove duplicated recovery-code persistence; test enable failure rollback, one-time response, existing-code redemption, repeated enable rejection, and migration review.
7. Apply explicit partitioned rate-limit annotations and test 429 behavior, partition separation, and unchanged Identity lockout. Update docs and rollout notes.

The current test project has unit coverage for a few Identity components but no full HTTP/Identity integration host. Add focused service tests plus a real-host or equivalent controller/integration harness for cookie, authorization, route, limiter, and Identity-store behavior. Validate from narrow to broad: affected project builds, filtered tests, `dotnet restore .\AhisApiTemplate.sln` if required, `dotnet build .\AhisApiTemplate.sln --no-restore`, then `dotnet test .\AhisApiTemplate.sln --no-build --no-restore`. Review the generated migration SQL without connecting to or updating a database.

Approval is required for this security/public-contract change and the Identity migration. The proposed defaults requiring owner confirmation are: (1) deliver the password-setup token by email after confirmation, with resend support; (2) remove the anonymous `check-account` and diagnostic routes; (3) use a five-minute 2FA challenge and `SameSite=Lax` at `/api` for refresh cookies; and (4) use the suggested limiter budgets or replace them with product-specific thresholds. Migration generation and migration application remain separate decisions. Do not deploy, apply migrations, or mutate external systems as part of verification.
