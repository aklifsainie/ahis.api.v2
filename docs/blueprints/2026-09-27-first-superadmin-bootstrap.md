# First Superadmin bootstrap prerequisite — Local Development

**Status:** Proposed for review. This blueprint authorizes no implementation, migration generation or application, CLI invocation, or deployment. Approval applies only to this file revision.

## Outcome and scope

Provide a one-time, Local Development-only CLI command to assign the existing `Superadmin` role to one explicitly identified eligible user. Require `--user-id <opaque-id>` and `--confirm-bootstrap`. Persist a permanent completion marker that also serves as a redacted audit record. A completed bootstrap must refuse every later invocation, including when no effective Superadmin remains.

Preserve the current uncommitted role-store alignment work and every historical blueprint. Do not add a public HTTP endpoint, P2 administrative or role-management endpoints, a recovery bootstrap, role claims, credential changes, or configuration-sourced target selection.

## Owning module and evidence

**Confirmed source:** `ahis.template.api/Program.cs` is the executable host. It uses `WebApplication.CreateBuilder(args)`, registers `AddIdentityCore<ApplicationUser>().AddRoles<IdentityRole>().AddEntityFrameworkStores<IdentityContext>()`, and runs the HTTP pipeline after `builder.Build()`. The launch profiles use `ASPNETCORE_ENVIRONMENT=Development`. No existing CLI dispatch or bootstrap command was found. `ahis.template.identity/IdentityServiceRegistration.cs` registers Identity services and SQL Server `IdentityContext`; `IdentityUnitOfWork` supplies an IdentityContext transaction. `ApplicationUser` has `IsActive`, `IsDeleted`, `EmailConfirmed`, and Identity lockout fields. `IdentityRestrictionService.IsAuthenticationAllowedAsync` denies active holds, unclassified restrictions, ambiguous legacy lockouts, inactive users, and deleted users. `IdentityTokenStateService.InvalidateAsync` rotates the security stamp and revokes refresh tokens and sessions. Registration does not assign a role.

**Role prerequisite:** The current working tree contains uncommitted `AlignIdentityRoleStoreAndSeedSystemRoles` migration, snapshot, test, and documentation edits. The migration targets `AspNetRoles`, seeds `Superadmin` and `User`, and assigns no users. The revised role-store blueprint `docs/blueprints/2026-09-27-identity-role-store-alignment-r5.md` and `docs/architecture/persistence.md` say application remains separately authorized. Do not edit or regenerate that work. Bootstrap may run only after the role-store migration is independently approved, applied to the named Local Development database, and verified there.

**Token and audit evidence:** `AuthenticationService` obtains current roles with `UserManager.GetRolesAsync` and places them in JWT `ClaimTypes.Role`. `Program.cs` has Superadmin policies and bearer validation of account state, security version, and session. Existing JWT role claims are snapshots. `AuditLogger` writes through a separate `ApplicationDbContext` and suppresses non-cancellation write failures; it cannot guarantee a bootstrap audit in the Identity transaction. Existing Identity restriction provenance is retained in `IdentityContext`.

## Proposed flow and CLI boundary

1. Add a dedicated `bootstrap-superadmin` branch at the API executable entry point, before building or starting the web app. Parse only the process argument array with a small exact parser: one command, exactly one nonblank `--user-id` value, and exactly one valueless `--confirm-bootstrap`; reject duplicates, unknown options, missing values, and extra positional arguments. Do not read the target ID from `IConfiguration`, environment variables, files, claims, or a default.
2. Require the resolved host environment name to be exactly `Development`, matching the repository launch profiles. Also fail closed unless the resolved SQL Server target can be verified as a local Development target; reject remote, ambiguous, or redirected data sources. Recheck the named target and its migration history before invocation. The environment label alone is insufficient proof of a local database.
3. Reuse the registered Identity DI services in a scoped CLI execution. Build the service provider without starting `app.Run`, listeners, Swagger, hosted cleanup, request middleware, or HTTP authentication. Reject the command before database access when arguments or environment fail. Return generic success/failure text and a nonzero exit code on refusal; never print email, token, credential, claim values, connection string, or detailed exception data. Avoid echoing the target ID. Suppress sensitive EF logging in this mode.
4. Have a dedicated `IFirstSuperadminBootstrapService` and Identity-owned implementation coordinate `UserManager<ApplicationUser>`, `RoleManager<IdentityRole>` or equivalent role-store reads, `IIdentityRestrictionService`, `IIdentityTokenStateService`, and `IdentityContext`. No custom mediator handler or controller is needed because there is no HTTP request. Do not borrow Country repositories or the audit query's Application-side EF exception.
5. In one serializable SQL Server transaction, first refuse if the singleton completion marker exists. Confirm the canonical normalized `SUPERADMIN` role exists exactly once in `AspNetRoles` and the role-store prerequisite is present. Refuse if any `IdentityUserRoles` row already grants Superadmin: this command establishes the first assignment and must not overwrite an existing administrative state. Find the exact opaque target ID. Require an active, non-soft-deleted, email-confirmed user with no Identity lockout and no active or ambiguous restriction; use the fail-closed provenance check, and reject any non-null `LockoutEnd` so an expired but unclassified legacy lockout cannot qualify. Reject a target with any existing role assignment, so its resulting role set is exactly `{Superadmin}` and no other role is removed silently. Recheck eligibility within the transaction immediately before mutation.
6. Assign Superadmin through the Identity role store, check the `IdentityResult`, and verify the target has exactly one resulting role assignment. Rotate its security stamp and revoke all existing refresh tokens and sessions within the same Identity transaction; this prevents existing access tokens or sessions from carrying stale role state. Insert the singleton redacted bootstrap marker with target ID and UTC completion time, save, and commit. Success means assignment, token invalidation, and marker all committed. A failure or cancellation rolls back all three. Do not send email or issue a token.

This CLI branch is a narrowly scoped authorization bypass: it has no authenticated actor, so its only admission controls are the exact command, explicit confirmation, Development and local-target checks, role-store prerequisite, strict user eligibility, no prior Superadmin assignment, and the durable one-time marker. It must never be reachable through routing, startup seeding, hosted services, or ordinary API traffic.

## Schema, migration, and durable audit

Use one new `IdentityContext` table, `FirstSuperadminBootstrap`, as both completion marker and minimal durable audit. Columns: `Id` tinyint, non-generated, primary key with a check constraint requiring `Id = 1`; `TargetUserId` required `nvarchar(450)`; `CompletedAtUtc` required `datetime2`. No email, username, token, credential, claim, freeform metadata, or foreign key: deleting or soft-deleting the target must not remove the permanent marker. Do not add a mutable completed flag or a reset path. The primary key and check constraint enforce at most one successful bootstrap independently of application code. The migration adds only this empty table and constraint; it must not modify roles, user-role relationships, users, or the existing role-store alignment migration. Review `Up`, `Down`, designer, snapshot, and generated SQL. `Down` may drop the table only if it is empty and must throw if the marker exists. A completed marker must survive ordinary upgrades, role removal, and supported rollback.

The marker is the authoritative redacted audit record. Do not rely on the cross-context best-effort `IAuditLogger`; a second audit entry could be considered only in a separately reviewed design and cannot replace the atomic marker. Limit marker access to database operators and future explicitly reviewed internal tooling.

For concurrency, use a serializable transaction, a SQL Server transaction-owned singleton lock or equivalent key-range locking, and the database primary key as the final guard. Keep role lookup, zero-existing-assignment check, target eligibility check, Identity role addition, token invalidation, marker insertion, and commit in that transaction. On a concurrent attempt, deadlock, uniqueness conflict, or uncertain commit result, fail closed and reread the marker before reporting success; never retry by assigning another target. Relational tests must prove that at most one concurrent attempt commits and that losing attempts leave no assignment or marker. Existing role-management paths are out of scope; if later code can write the same role concurrently, its coordination requires a separate review.

## Token, authorization, and rollback effects

A new login after commit obtains the Superadmin role claim. Existing JWTs are not rewritten; security-stamp rotation makes old access tokens fail bearer validation, and the same transaction revokes refresh tokens and sessions. Existing Superadmin policies then work only with a newly authenticated eligible target. The CLI itself bypasses HTTP bearer policies by design and does not grant API-client permissions.

Before a successful invocation, an empty-table migration rollback may be reviewed separately. After success, do not run `Down` or erase the marker to enable another bootstrap. If a database restore is proposed, the recovery plan must preserve the completed marker and its target/time evidence; restoring an earlier database image without it would violate the once-ever rule. If the target later loses Superadmin or becomes ineligible, the CLI remains permanently closed. Recovery or reassignment needs a separate authorized design; this blueprint contains no recovery command.

## Risks, assumptions, and open decisions

**Risks:** a Development label can point at a nonlocal database; command-line arguments may appear in local process inspection; existing JWTs would otherwise retain stale roles; a best-effort cross-context audit could be lost; a race could create multiple assignments without transactional and database guards; dropping a used marker or restoring a pre-bootstrap backup would reopen bootstrap. Fail closed on uncertain environment, schema, eligibility, or commit state.

**Assumptions and inferences:** `Development` is the repository's Local Development host label, as shown by launch profiles; it is not proof of database locality. The owner-confirmed phrase “assign exactly Superadmin” is implemented by requiring the target to have no pre-existing role, so the command never removes another role. The current source shows no general role-assignment endpoint. Source review does not establish live database state.

**Open decisions before later gates:** agree on the precise local SQL Server allowlist and verification method for the selected Local Development setup; select an isolated disposable SQL Server test fixture and its approval path; confirm the named database's applied migration history and absence of a prior Superadmin assignment; choose the operator, backup/restore method, and invocation window. None permits the command to run outside Local Development or changes the one-time rule.
