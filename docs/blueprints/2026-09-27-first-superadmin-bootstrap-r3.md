# First Superadmin bootstrap prerequisite — revision 3

**Status:** Proposed for review. This revision supersedes `docs/blueprints/2026-09-27-first-superadmin-bootstrap-r2.md` for future implementation. Preserve r2 and the original blueprint as historical context. Approval applies only to this reviewed revision. This blueprint authorizes no implementation, migration generation or application, database connection, CLI invocation, or deployment.

## Outcome and scope

Provide a one-time, CLI-only `bootstrap-superadmin` command in the API executable. In Local Development, it assigns the existing `Superadmin` role to one explicitly identified eligible user. Require exactly one `--user-id <opaque-id>` and one valueless `--confirm-bootstrap`. A permanent completion marker is also the redacted audit record; every later invocation refuses, even if no effective Superadmin remains.

**Owner decision:** The fixed `ahis.template.api/appsettings.development.json` file is the approved Local Development configuration trust root. The repository's on-disk casing is `ahis.template.api/appsettings.Development.json`; implementation must resolve that existing fixed file, including on case-sensitive filesystems, without accepting an alternate path. Before creating an Identity connection, validate the single `ConnectionStrings:DefaultConnection` value from that file for exact TCP IP, private IPv4, and database syntax. Independently attest the *actual physical* SQL endpoint, TCP transport and port, and current database only at CLI runtime, on the same open connection immediately before its serializable transaction. No separate static independent-vetting configuration source or target allowlist setting is required or permitted.

The sole admitted target is the owner-confirmed TCP IPv4 literal `172.20.198.156` and database `AhisApiTemplateV2Db`, with an attested default TCP port of `1433`. `ASPNETCORE_ENVIRONMENT` must equal `Development` exactly. No public endpoint, startup seeding, hosted bootstrap, P2 administration or role management, recovery flow, role claims, credential change, or production configuration change is in scope.

## Owning module, evidence, and confidence

**Confirmed source facts:** `ahis.template.api/Program.cs` calls `WebApplication.CreateBuilder(args)`, reads `DefaultConnection`, registers Identity, and later runs the HTTP host. `ahis.template.identity/IdentityServiceRegistration.cs` registers `IdentityContext` with SQL Server. The development JSON file exists; this planning task did not print or verify its connection value. `IdentityTokenStateService` rotates the security stamp and revokes refresh tokens and sessions. The authentication documentation describes version and session validation for JWTs. The current tree contains uncommitted role-store migration, model, test, and documentation work that implementation must preserve. No live SQL endpoint, migration history, user eligibility, or database contents were verified.

**Owner-confirmed rules:** The file above is the static trust root; the exact Development, IP, and database values are admission requirements. The IP lies within the private `172.16.0.0/12` IPv4 range. The physical endpoint and current database require runtime attestation; static configuration alone cannot establish them.

**Existing prerequisite:** The separate role-store alignment migration targets `AspNetRoles`, seeds canonical `Superadmin` and `User` roles, and assigns no users. Its application to the named Development database remains a separate approval and verification gate.

## Observed and proposed flow

Observed HTTP flow: API host configuration → Identity registration and `IdentityContext` → authentication and current-role JWT issuance → existing bearer validation and protected actions. Bootstrap has no HTTP request or authenticated actor.

Proposed CLI flow: early command dispatch → strict argument and process-environment checks → isolated load and validation of the fixed development JSON value → creation of an Identity connection from that vetted value → runtime attestation of the physical SQL target on that connection → immediate serializable transaction on the same connection → schema, marker, role, assignment, and eligibility checks → role assignment, token-state invalidation, marker insertion, and commit. Refusals return a generic nonzero result without Identity mutation or sensitive output.

## CLI admission and fail-closed design

1. Dispatch `bootstrap-superadmin` before `WebApplication.CreateBuilder(args)` and before any host startup, listener, middleware, Swagger, cleanup service, or HTTP authentication. Accept only the exact command, one nonblank `--user-id` value, and one valueless `--confirm-bootstrap`. Reject duplicate or unknown options, missing values, and extra positional arguments. Obtain the opaque target ID only from that argument; never use configuration, environment, files, claims, or a default. Do not echo it.
2. Require the process variable `ASPNETCORE_ENVIRONMENT` to equal `Development` with an ordinal, case-sensitive comparison. Reject absence, alternate casing, and conflicting host-environment input such as `DOTNET_ENVIRONMENT`. Complete argument and environment checks before database access.
3. Resolve only the existing fixed development JSON in the API project/content root; do not accept a caller-selected file, working-directory substitute, configuration target, or fallback. Load its single `ConnectionStrings:DefaultConnection` value in isolation. Reject missing, null, blank, malformed, duplicate, or ambiguous sections or keys. Detect and reject attempts to supply or override that key through environment variables, including provider-specific connection-string aliases, command-line input, user secrets, or other configuration providers, even if an override repeats the approved value. Register `IdentityContext` only with the vetted file value, never a merged value. Do not print it or its credentials.
4. Before constructing or opening an Identity connection, parse the file value with the SQL Server connection-string parser and independently detect duplicate synonymous keys that last-value-wins parsing could conceal. Normalize recognized data-source and database aliases. Accept only an unambiguous TCP prefix followed by a canonical four-octet IPv4 literal; after prefix-case normalization, require exactly `tcp:172.20.198.156`. Independently parse and verify private IPv4. Require the database or initial catalog to equal `AhisApiTemplateV2Db` by ordinal comparison. Reject whitespace or controls inside the address, shorthand, hexadecimal, octal, IPv6, hostname, DNS alias, explicit port, named instance, LocalDB, named pipe, or any suffix. Reject duplicate or conflicting `Server`/`Data Source` and `Database`/`Initial Catalog` forms even when their final values match.
5. Reject failover partner, read-only or application-intent routing, multi-subnet routing, client network-library or alias selection, attach-file or user-instance selection, and unknown or ambiguous endpoint-affecting options. Never resolve a hostname to justify admission. If the fixed JSON cannot pass, stop and seek a revised reviewed plan; do not change configuration or weaken admission.
6. Only after static validation, open the vetted SQL connection at CLI runtime. On that same physical open connection, obtain SQL Server evidence of TCP transport, local network address `172.20.198.156`, local TCP port `1433`, and `DB_NAME()` equal to `AhisApiTemplateV2Db`. Require complete, consistent evidence; reject null or unavailable metadata, client aliasing, failover, redirection, or a mismatched endpoint. Attest immediately before beginning the serializable transaction and bind the Identity context and transaction to that connection. Reject an automatic reconnect or connection replacement unless the new physical connection is independently re-attested before any transaction or mutation; fail closed if continuity cannot be proven. The static JSON is the approved source of the intended target, while this runtime check proves where the connection actually landed. Do not require a second static configuration file, independent static attestation value, or allowlist setting.
7. Execute through a scoped CLI service provider using existing Identity registrations without `app.Run`. Suppress sensitive EF logging and detailed exception output in CLI mode. Return only generic success or refusal; refusal has a nonzero exit code. `--confirm-bootstrap` is a runtime guard, not authorization for the state-changing invocation.

## Business behavior, authorization, and API contract

Use an Identity-owned `IFirstSuperadminBootstrapService` implementation coordinating `UserManager<ApplicationUser>`, role-store reads, `IIdentityRestrictionService`, `IIdentityTokenStateService`, and `IdentityContext`. The API project owns CLI parsing, static admission, and connection attestation. There is no controller, mediator handler, API route, public contract, or bearer policy for this command. It is a narrowly scoped authorization bypass with no authenticated actor.

Inside one serializable transaction, refuse if the singleton marker exists. Require the independently applied role-store prerequisite and exactly one canonical `SUPERADMIN` role in `AspNetRoles`; refuse if any user-role row already grants Superadmin. Find the exact opaque target ID. Require an active, non-soft-deleted, email-confirmed user with no Identity lockout, active restriction, unclassified restriction, or ambiguous legacy lockout. Reject every non-null `LockoutEnd`, including an expired value. Reject any pre-existing role assignment so the resulting role set is exactly `{Superadmin}` without removing another role. Recheck eligibility immediately before mutation.

Assign through the Identity role store, inspect `IdentityResult`, and verify exactly one resulting role assignment. In the same transaction rotate the security stamp, revoke all existing refresh tokens and sessions, insert the redacted singleton marker, save, and commit. A new login may then receive the role claim; existing JWTs and sessions must fail current validation. Send no email and issue no token. Cancellation or failure rolls back assignment, invalidation, and marker together. Never retry an uncertain commit by assigning another target.

## Persistence, transaction, migration, and audit

Add one `IdentityContext` table, `FirstSuperadminBootstrap`, as the permanent completion marker and redacted audit. Columns: non-generated `Id` tinyint primary key with a check constraint requiring `Id = 1`; required `TargetUserId` `nvarchar(450)`; and required `CompletedAtUtc` `datetime2`. Store no email, username, token, credential, claim, connection detail, or freeform metadata. Do not add a foreign key, mutable completed flag, or reset path. User deletion must not remove the marker. The primary key and check constraint enforce at most one completion independently of application logic.

The new migration adds only an empty marker table and constraint. It must not alter users, roles, user-role rows, or the role-store alignment migration. Review `Up`, `Down`, designer, snapshot, and generated SQL. `Down` may drop the table only while empty and must throw if a marker exists. A completed marker must survive ordinary upgrades, role removal, and supported rollback.

Use one serializable SQL Server transaction on the just-attested connection, a transaction-owned singleton lock or equivalent key-range guard, and the database primary key as the final concurrency guard. Keep role lookup, zero-existing-assignment check, eligibility checks, role addition, token and session invalidation, marker insert, and commit inside it. Deadlock, uniqueness conflict, concurrent attempt, cancellation, or uncertain commit fails closed; reread the marker only to determine whether a commit occurred, without attempting another assignment. At most one concurrent attempt may commit. Existing role-management paths need separate coordination review if they can write concurrently.

The marker is the authoritative audit. The cross-context, best-effort `IAuditLogger` cannot replace it. Limit marker access to database operators or future separately reviewed internal tooling.

## Security and rollback

Controls are exact command and confirmation, exact Development environment, fixed JSON trust-root validation before connection, physical runtime attestation on the transaction connection, independently applied role-store prerequisite, strict eligibility, absence of prior Superadmin assignment, atomic token invalidation, and a permanent marker. The command must never be reachable through routing, normal startup, hosted services, or ordinary traffic. Do not log the target ID, connection string, credentials, tokens, unmasked exceptions, or sensitive audit values. An opaque command-line ID may still be visible to local process inspection.

Before success, rollback of an empty-table migration may be considered through separate review. After success, never run `Down`, erase the marker, or restore a pre-bootstrap image to reopen bootstrap. A proposed restore must preserve completion evidence. If the target later loses Superadmin or becomes ineligible, the CLI remains closed. Recovery or reassignment requires a separate authorized design. Any inability to prove the actual SQL endpoint or port results in no Identity mutation.

## Risks, assumptions, and open decisions

**Risks:** A Development label or approved-looking connection string can still land on an unintended database through providers, SQL aliases, failover, or redirects. Ambiguous synonyms can conceal substitution. Metadata permissions may prevent physical attestation; that must fail closed. Existing JWTs can retain stale claims without atomic invalidation. Concurrent attempts, cross-context audit writes, or removal of the marker can defeat one-time behavior. The actual file casing matters on case-sensitive filesystems.

**Assumptions:** The owner-confirmed file, IP, and database are the only Local Development trust root and target. A port-free TCP IPv4 data source implies default port `1433`, which must be attested at runtime rather than inferred as a live fact. The fixed JSON's present value, physical endpoint, database state, and user eligibility were not verified in this read-only planning task. Requiring no existing target role realizes the resulting-role rule without removing roles. No separate static independent-vetting source or allowlist setting is needed.

**Open decisions for later gates:** Select an isolated SQL Server test fixture and its approval path; verify migration history and absence of an existing Superadmin assignment in the named database; select the eligible opaque target ID outside configuration; and choose operator, backup/restore method, and invocation window. The trust root, target IP, port, database, Development-only rule, and one-time semantics are settled and may not be relaxed through these decisions.
