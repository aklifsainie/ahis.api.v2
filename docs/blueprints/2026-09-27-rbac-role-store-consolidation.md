# Blueprint: RBAC role-store consolidation

**Status:** Draft for review. No implementation, migration generation, database access, build, or test is authorized by this task.

## Direct diagnosis for Hermes

The model contains two distinct EF role entity types. `Program.cs:397–398` registers `IdentityRole` for ASP.NET Core Identity, and the current migration snapshot maps that type to `AspNetRoles`. `IdentityContext.cs:30–33` separately registers and maps its base type, `IdentityRole<string>`, to `IdentityRoles`. The initial Identity migration creates both tables; `IdentityUserRoles.RoleId` and `IdentityRoleClaims.RoleId` reference `AspNetRoles`, and only `AspNetRoles.NormalizedName` has the Identity role-name index (`20260824144538_IdentityInitialMigration.cs:14–40, 113–117, 172–176, 205–210`). Thus a role created through the configured `RoleManager<IdentityRole>` would go to `AspNetRoles`; a direct EF insertion of `IdentityRole<string>` would go to `IdentityRoles`. Current repository source contains no committed role-creation endpoint, service, seed, or role-insert migration, so it does not demonstrate any current application request that creates a role. Live database contents and applied migration history have not been inspected.

## Outcome and scope

Make one Identity role entity and table authoritative for future RBAC work while preserving existing role IDs, user assignments, claims, and authorization behavior. Recommend retaining `IdentityRole` and `AspNetRoles`, then removing the redundant `IdentityRole<string>` mapping and, after a separate data inventory, retiring `IdentityRoles` safely. This blueprint covers investigation and the proposed role-store repair. Role-management endpoints, assignment endpoints, administrator bootstrap, and deployment are separate product and approval decisions.

## Confirmed facts and authoritative evidence

- `IdentityContext : IdentityDbContext<ApplicationUser>` calls `base.OnModelCreating(builder)` and then explicitly maps `IdentityRole<string>` to `IdentityRoles` (`ahis.template.identity/Contexts/IdentityContext.cs:8, 20–33`). `ApplicationUser` inherits `IdentityUser` (`Models/Entities/ApplicationUser.cs:6`). The explicit base-type registration is the source of the extra mapped role entity.
- The API registers `AddIdentityCore<ApplicationUser>().AddRoles<IdentityRole>().AddEntityFrameworkStores<IdentityContext>()` (`ahis.template.api/Program.cs:369–401`). This is the configured Identity manager/store role type. `IdentityServiceRegistration.cs:22–35` registers `IdentityContext` with SQL Server.
- The latest `IdentityContextModelSnapshot.cs:25–69` maps `Microsoft.AspNetCore.Identity.IdentityRole` to `AspNetRoles` with a unique filtered `RoleNameIndex` on `NormalizedName`, and separately maps `Microsoft.AspNetCore.Identity.IdentityRole<string>` to `IdentityRoles` without that index. Snapshot relationships at lines 536–568 point role claims and user-role links to `IdentityRole`, not `IdentityRole<string>`. The initial migration creates the two tables and foreign keys as described in the diagnosis. Later migration designers retain both mappings; no committed Identity migration inserts role rows (`rg` inspection of non-designer Identity migrations).
- Actual creation-path classification: (1) a future or external call to the configured `RoleManager<IdentityRole>.CreateAsync` uses the `IdentityRole` entity mapped to `AspNetRoles`; (2) a direct `IdentityContext.Set<IdentityRole<string>>().Add` or model seed of that base type targets `IdentityRoles`; (3) direct `IdentityContext.Set<IdentityRole>().Add` targets `AspNetRoles`. Paths (2) and (3) describe what the present model would do, not application code found in this repository. There is no current controller, service, seeder, or migration that calls these creation paths. The previous draft `docs/blueprints/2026-09-25-identity-role-store-alignment.md:14` reports a discarded, unapplied trial migration inserting into `IdentityRoles`; that is historical plan evidence, not a committed creation path or evidence of live data.
- `AuthenticationService.cs:883–888` gets user roles with `UserManager.GetRolesAsync` and copies them into JWT `ClaimTypes.Role` claims. `Program.cs:102–129` requires `Superadmin` for three administrative policies. `AccountService.cs:548–557` additionally checks current `Superadmin` membership for unlock. `Security/IdentityRoleNames.cs:3–7` defines `Superadmin` and `User`. `AdminIdentityController.cs:30,55,100` applies the administrative policies. These are consumers of roles, not role creators.
- The backlog (`docs/backlog/identity-security-endpoints.md`, P2 User role management) describes proposed RBAC endpoints and calls for `RoleManager<IdentityRole>` and `UserManager<ApplicationUser>`; they are not implemented. Current tests include a mocked `IsInRoleAsync` unlock check but no role-store, role-creation, migration, or end-to-end authorization test (`ahis.template.test/TestFeatures/AccountFeature/UnlockAdminUserAccountServiceTest.cs`).

## Owning module and dependencies

`ahis.template.identity` owns the Identity model, role storage, migrations, and prospective role services. `ahis.template.api` owns Identity registration and authorization policies. Account and Authentication consume roles through Identity managers. This work depends on the Identity SQL Server context and its separate migration history; `ApplicationDbContext` and API-client permission storage belong to other modules and must not be merged into this RBAC store. Follow the Account and Authentication `AGENTS.md` service boundary and the repository's custom mediator if future HTTP role endpoints are separately approved.

## Proposed flow and implementation sequence

1. Under separately authorized, read-only database inspection for each target environment, inventory `__EFMigrationsHistory`, both role tables, their schema and row counts, normalized-name collisions, `IdentityUserRoles`, `IdentityRoleClaims`, actual foreign keys, indexes, and any external writers. Record whether initial and later Identity migrations were applied. Source alone cannot establish live contents.
2. Confirm `AspNetRoles` as the authoritative store if deployed schema and data agree with the committed foreign keys. Keep `AddRoles<IdentityRole>()`; change `IdentityContext.OnModelCreating` to map that exact type explicitly to `AspNetRoles` and remove the explicit `IdentityRole<string>` entity mapping. Verify that the resulting EF model has one role entity, one role-name index, and both relationships pointing to it. Preserve role IDs and normalized names.
3. Generate and review a new `IdentityContext` migration only after step 1 and approval of the exact data plan. If `IdentityRoles` is empty everywhere, a guarded retirement of that table may be appropriate. If populated, reconcile rows by stable ID and normalized name, resolve collisions and any external references, then specify transactional transfer or retention and a reversible rollback strategy. Never silently drop populated role data or repoint relationships by assumption. Review generated `Up`, `Down`, designer, and snapshot; hand-review any data guards or SQL before use. Do not rewrite an already applied initial migration.
4. Validate role creation and lookup via `RoleManager<IdentityRole>`, assignment and retrieval via `UserManager<ApplicationUser>`, role claims, JWT issuance, and affected administrative policies against the repaired model. Only after store repair and approved data review should a separate initial-role seed or bootstrap plan proceed. Do not seed `Superadmin` into either table merely to make an existing policy pass.

## Business behavior, authorization, API, audit, and integration impact

The proposed store repair introduces no role-creation API, role assignment, or new public response shape. Existing `Superadmin` policies must continue to resolve against roles linked through `IdentityUserRoles`. JWT role claims are snapshots at issuance; newly assigned roles require a fresh token, while removed privileges in an already issued token raise a separate revocation decision. The unlock service's fresh membership check is narrower than the other policy-only administrative paths. Do not infer that database role removal immediately invalidates every bearer. Decide token invalidation before implementing mutable RBAC. Role and assignment changes, when later approved, need redacted actor/target audit records and a defined transaction boundary; the store repair itself should not create audit entries for fabricated business actions. No email or external integration is needed for the mapping repair.

## Data and migration risks

`AspNetRoles` is the source-supported direction because the configured runtime type, role-name index, and committed user-role and role-claim foreign keys all use it. This recommendation is conditional on the target database inventory. A populated `IdentityRoles` table may contain manually inserted, seeded, or external data invisible to current user-role relationships. Duplicate IDs or normalized names, divergent role names, unknown external foreign keys, migration drift, and different environments require explicit reconciliation. A generated `DropTable(IdentityRoles)` is unsafe until the table is verified empty or its data is accounted for. Rollback after data consolidation may require a documented backup and forward-only recovery rather than a destructive automatic `Down`. Migration generation, migration application, and administrator provisioning require separate approvals. Never run `dotnet ef database update` as verification.

## Assumptions and open product/security decisions

**Assumption:** The committed model represents the intended runtime wiring; live data and external writers remain unknown. **Open decisions:** confirm the authoritative target table after environment inventory; decide treatment of any `IdentityRoles` rows and name/ID conflicts; approve whether `Superadmin` and `User` form the initial protected catalog and how the first administrator is provisioned; decide whether human permissions use roles alone or role claims; define role read/manage/assign policies, step-up, self-change and last-administrator safeguards, and role-change token/session invalidation. Review whether the existing security-read policy should explicitly constrain the bearer scheme like the other administrative policies. These choices must be settled in a revised or separate approved blueprint before they change public API or security behavior.
