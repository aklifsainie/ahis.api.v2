# First Superadmin bootstrap prerequisite — revision 2

**Status:** Proposed for review. This revision supersedes `docs/blueprints/2026-09-27-first-superadmin-bootstrap.md` for future implementation; preserve that file as historical context. Approval applies only to this revision. This plan authorizes no implementation, migration generation or application, CLI invocation, database access, or deployment.

## Outcome and scope

Provide a one-time, CLI-only command in the API executable that assigns the existing `Superadmin` role to one explicitly identified eligible user in Local Development. Require exactly one `--user-id <opaque-id>` and one valueless `--confirm-bootstrap`. A permanent completion marker also serves as the redacted audit record. Every later invocation must refuse, even if no effective Superadmin remains.

The owner-confirmed database admission rule is exact: `ASPNETCORE_ENVIRONMENT` must be exactly `Development`, and the CLI's effective connection must come solely from `ConnectionStrings:DefaultConnection` in `ahis.template.api/appsettings.development.json`, with a normalized data source of exactly `tcp:172.20.198.156` and a database of exactly `AhisApiTemplateV2Db`. The address must also pass a private IPv4 check. Refuse any other host, port, instance, database, missing or ambiguous setting, DNS alias, redirected target, or configuration override. The CLI must never obtain the target user ID from configuration.

Do not add a public endpoint, startup seeding, hosted bootstrap, P2 administrative or role-management work, a recovery flow, role claims, credential changes, or production configuration changes.

## Observed and proposed flow

Observed HTTP flow: API host registration → Identity manager and services → `IdentityContext`; authentication reads roles into JWT claims, and bearer validation and Superadmin policies govern existing protected actions. The bootstrap has no HTTP request or authenticated actor.

Proposed CLI flow: parse process arguments → check the exact process environment and isolated JSON configuration → validate and attest the database target → create a scoped Identity service execution without starting HTTP → check schema, one-time state, role, and target eligibility inside a serializable Identity transaction → assign the role, invalidate token state, insert the marker, and commit. All refusal paths return a generic nonzero result without mutation or sensitive output.

## CLI admission and fail-closed design

1. Dispatch `bootstrap-superadmin` before `WebApplication.CreateBuilder(args)` or any host startup that could start listeners, middleware, Swagger, cleanup services, or HTTP authentication. The parser accepts only the command, one nonblank `--user-id` value, and one `--confirm-bootstrap`; reject duplicate or unknown options, missing values, and extra positional arguments. Read the target ID only from that process argument. Do not fall back to configuration, environment, files, claims, or a default. Do not echo the ID.
2. Require the process variable `ASPNETCORE_ENVIRONMENT` to equal `Development` using an ordinal, case-sensitive comparison. Reject absent or differently cased values, and reject a conflicting host-environment setting such as `DOTNET_ENVIRONMENT`. Perform argument and environment checks before any database access.
3. Resolve the expected, fixed `ahis.template.api/appsettings.development.json` path from the API project/content root without accepting an alternate file or working-directory substitute. Load only its single `ConnectionStrings:DefaultConnection` value for the CLI. Reject a missing, null, blank, malformed, duplicate, or ambiguous section/key. Inspect configuration provenance and reject any environment, command-line, user-secret, alternate-file, or other provider override of that key, including provider-specific connection-string environment aliases. The connection registered with `IdentityContext` must be the vetted value from this file; never use a merged or substituted value. Do not print the value or its credentials.
4. Parse the value with the SQL Server connection-string parser, while separately detecting duplicate synonymous keys before last-value-wins parsing can hide them. Normalize recognized data-source and database key aliases to their canonical properties. For the data source, accept only an unambiguous TCP prefix and a canonical four-octet IPv4 literal; normalize the prefix's case, then require the resulting data source to be exactly `tcp:172.20.198.156`. Independently parse the address as IPv4 and verify it is private. Require the parsed database/initial catalog to equal `AhisApiTemplateV2Db` by ordinal comparison. Reject whitespace or control characters inside the address, shorthand, hexadecimal, octal, IPv6, hostname or DNS alias, explicit port, named instance, LocalDB, named pipe, or any other suffix. Reject duplicate or conflicting `Server`/`Data Source` and `Database`/`Initial Catalog` forms, even when their final values would match.
5. Reject connection-string features that can redirect or choose another endpoint or catalog, including a failover partner, read-only/application-intent routing, multi-subnet routing, client network-library or alias selection, attach-file/user-instance selection, and unknown or ambiguous endpoint-affecting options. Do not resolve a hostname to justify admission. If the current JSON cannot satisfy these checks without changing configuration, stop and request a revised approved plan; do not weaken the checks.
6. Before any Identity read or mutation, open the vetted SQL connection and attest the actual connected target on that same connection. Require SQL Server to report TCP transport, local network address `172.20.198.156`, default TCP port `1433` with no configured port or instance, and current database `AhisApiTemplateV2Db`. Reject null, unavailable, inconsistent, or unexpected attestation, client aliasing, failover, redirection, or a reconnect to a different endpoint. Keep the attested physical connection for the transaction and recheck after any reconnect and immediately before mutation. If the implementation cannot prove these properties, fail closed. Do not query or print server credentials or the connection string.
7. Use a scoped CLI service provider with existing Identity registrations and the vetted connection, without calling `app.Run`. Return only generic success or refusal and a nonzero exit code on refusal. Suppress sensitive EF logging and detailed exception output in CLI mode. The confirmation flag is a runtime guard, not authorization to invoke the command.

The exact numeric IP and database replace the earlier blueprint's open local-target allowlist decision. `Development` alone is insufficient. No alternate target, port, instance, redirect, or configuration override is permitted as a fallback.

## Business behavior and authorization

Use an Identity-owned `IFirstSuperadminBootstrapService` implementation coordinating `UserManager<ApplicationUser>`, `RoleManager<IdentityRole>` or equivalent role-store reads, `IIdentityRestrictionService`, `IIdentityTokenStateService`, and `IdentityContext`. This is a CLI command, so it needs no controller, custom mediator handler, API route, or bearer policy. Do not use Country repositories or the audit query's Application-side EF exception.

Inside one serializable transaction, refuse if the singleton marker already exists; require the independently applied role-store prerequisite and exactly one canonical `SUPERADMIN` role in `AspNetRoles`; and refuse if any user-role row already grants Superadmin. Find the exact opaque target ID. Require an active, non-soft-deleted, email-confirmed user with no Identity lockout, active restriction, unclassified restriction, or ambiguous legacy lockout. Reject any non-null `LockoutEnd`, including an expired one. Reject any pre-existing role assignment so the resulting role set is exactly `{Superadmin}` without silently removing another role. Recheck eligibility immediately before mutation.

Assign the role through the Identity role store, inspect `IdentityResult`, and verify exactly one resulting role assignment. In the same transaction, rotate the target's security stamp and revoke all existing refresh tokens and sessions, insert the redacted singleton marker, save, and commit. A new login can then receive the Superadmin role claim; old JWTs and sessions must fail existing validation. Send no email and issue no token. Cancellation or any failure rolls back assignment, invalidation, and marker together. Never retry an uncertain commit by assigning another target.

## Persistence, transaction, migration, and durable audit

Add one `IdentityContext` table, `FirstSuperadminBootstrap`, as both the permanent completion marker and redacted audit. Columns: non-generated `Id` tinyint primary key with a check constraint requiring `Id = 1`; required `TargetUserId` `nvarchar(450)`; and required `CompletedAtUtc` `datetime2`. Store no email, username, token, credential, claim, connection detail, or freeform metadata. Do not add a foreign key, mutable completed flag, or reset path; deleting or soft-deleting the user must not remove the marker. The primary key and check constraint enforce at most one completion independently of application logic.

The new migration adds only the empty marker table and constraint. It must not alter users, roles, user-role rows, or the role-store alignment migration. Review `Up`, `Down`, designer, snapshot, and generated SQL. `Down` may drop the table only while empty and must throw if a marker exists. A completed marker must survive ordinary upgrades, role removal, and supported rollback.

Use one serializable SQL Server transaction, a transaction-owned singleton lock or equivalent key-range guard, and the database primary key as the final concurrency guard. Keep role lookup, zero-existing-assignment check, eligibility checks, role addition, token and session invalidation, marker insert, and commit inside that transaction on the attested connection. On a deadlock, uniqueness conflict, concurrent attempt, cancellation, or uncertain commit, fail closed; reread the marker only to determine whether a commit occurred, without attempting another assignment. At most one concurrent attempt may commit. Existing role-management paths remain outside this blueprint and need separate coordination review if they can write concurrently.

The marker is the authoritative audit. The cross-context, best-effort `IAuditLogger` cannot replace it. Limit marker access to database operators or future separately reviewed internal tooling.

## Security and rollback

The CLI is a narrowly scoped authorization bypass because it has no authenticated actor. Its controls are the exact command and confirmation, exact Development and database admission, connected-endpoint attestation, independently applied role-store prerequisite, strict target eligibility, absence of a prior Superadmin assignment, atomic token invalidation, and permanent marker. It must never be reachable through routing, normal startup, hosted services, or ordinary traffic. Do not log the user ID, connection string, credentials, token material, unmasked exception data, or sensitive audit values. Command-line arguments may be visible to local process inspection; use only an opaque target ID.

Before success, rollback of an empty-table migration may be considered through a separate review. After success, never run `Down`, erase the marker, or restore a pre-bootstrap image as a way to reopen bootstrap. A proposed database restore must preserve the completion marker and its target/time evidence. If the target later loses Superadmin or becomes ineligible, the CLI remains closed. Recovery or reassignment requires a separate authorized design; this plan has no recovery flow. Admission failure, including inability to prove the actual SQL endpoint or port, must produce no Identity mutation.

## Risks, assumptions, and open decisions

**Risks:** a Development label can point to an unintended database; configuration providers, SQL aliases, failover, or redirects can change the effective target; ambiguous connection-string synonyms can hide a last-value-wins substitution; command-line IDs can appear in local process inspection; existing JWTs can retain stale role claims; cross-context audit writes can be lost; concurrent attempts can assign multiple users without transaction and database guards; dropping or restoring away a completed marker can reopen bootstrap. Reject uncertainty at every admission and commit boundary.

**Assumptions:** the owner-confirmed address and database are the only allowed Local Development target. A port-free TCP IPv4 data source implies the default SQL Server TCP port `1433`; the CLI must attest that port rather than assume it. The exact setting's current value and the live database state were not verified during this read-only planning task. Requiring the target to have no role implements the previously confirmed resulting-role rule without removing other roles.

**Open decisions before later gates:** choose an isolated SQL Server test fixture and its approval path; verify the named database's migration history and absence of any prior Superadmin assignment; identify the eligible opaque target ID outside configuration; and select the operator, backup/restore method, and invocation window. The server, port, database, Development-only rule, and one-time semantics are settled and may not be relaxed through these decisions.
